# ADR-0051: Dashboard schema architecture — persist generated snapshots

Status: Accepted. Context: NXS-DASH-001 requires a backend-owned, versioned dashboard schema contract that a later frontend renders safely. Decision: the canonical tenant dashboard schema is a strongly validated, versioned data contract (`schema_version`, `organization_id`, `revision`, sections of widgets with stable keys, titles, visibility, ordering, data-source identifiers and registry-controlled permission requirements). Widget definitions are DATA ONLY: config values are bounded flat primitives under a conservative key denylist (exec/sql/url/hook/…), extra fields are forbidden, and nothing in a schema is ever executed.

**Persist-vs-regenerate:** the PROVISIONER persists the generated snapshot (`dashboard_configurations`, one canonical row per (organization, revision)). Deterministic regeneration is the rebuild/verification path, not the serving path. Rationale: persisted snapshots give independent validateability, explicit revisions and a migration path between schema versions; regeneration stays deterministic for identical inputs (registry order, registry-controlled permissions) so the two can never diverge silently — every stored schema MUST revalidate against the registry (and its schema_version column) before serving, and unknown widgets / unregistered data sources / permission tampering / unsupported versions fail closed.

**Allow-list:** `WIDGET_REGISTRY` holds the small, correct baseline: `organization.profile`, `organization.provisioning_status`, `organization.settings_summary` — control-plane data that genuinely exists by P05. Future domains register their own widgets in their own phases; nothing fakes conversations, channels, campaigns or any later-domain data. A tenant can never inject an unregistered widget, reference an unregistered data source, or grant itself permissions through dashboard configuration.

**Permission filtering:** `GET /organizations/current/dashboard-schema` requires `dashboard:read` and projects the schema to exactly the widgets whose `required_permissions` the viewer holds — an ordinary member gets only their permitted view, by construction. Consequences: P05 builds no visual UI and no configuration API; the schema is a stable contract a later frontend and later configuration surfaces can consume and extend.
