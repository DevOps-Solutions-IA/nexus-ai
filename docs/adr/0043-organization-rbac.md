# ADR-0043: Organization-scoped RBAC

Status: Accepted. Context: P03 owns the foundational authorization boundary. Decision: stable permission identifiers live in a global catalog (`organization:read`, `organization:write`, `membership:manage`, `role:assign`, `auth:session:read`); roles are global catalog definitions (`org_owner`, `org_admin`, `org_member`) seeded deterministically by the migration; role ASSIGNMENTS are tenant-owned rows under forced RLS. Authorization always resolves assignments in the caller's Organization scope through the deny-by-default `AuthorizationService`: no permission means denial, never a default grant; there is no implicit admin by email/domain/name; an assignment in Organization A grants nothing in Organization B (RLS makes that a database guarantee). Assignment status (ACTIVE/SUSPENDED) is checked per evaluation, so suspension takes effect immediately. Unknown role keys land in the catalog lookup and are denied — the service never trusts the shape of a caller-supplied role value. Consequences: no ABAC/policy engine is built (P03 scope); the provisioner (P05) creates the first membership+owner assignment through the internal bootstrap seam; `tests/integration/test_auth_rbac.py` proves escalation, forgery, cross-tenant reuse and inactive assignments all fail closed.
