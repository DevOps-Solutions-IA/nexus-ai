# ADR-0041: Token and session architecture

Status: Accepted. Context: P03 needs a production-capable, provider-extensible, fail-closed token model. Decision: short-lived access tokens (15 min default, bounded 1–60 min) are EdDSA JWTs carrying `iss`, `aud`, `sub` (user_id), `org` (organization_id), `sid` (session_id), `jti`, `iat`, `nbf`, `exp`, with a `kid` header and `typ=access`. Verification is fail-closed: single-algorithm allowlist (EdDSA only — HS256 confusion and `alg=none` are refused by construction), explicit issuer/audience equality, all seven claims required, bounded clock skew (30 s default, 0–120 s) validated explicitly against the injected clock, unknown `kid` rejected, and `typ` enforced by the verifier itself. Refresh tokens are opaque 256-bit random strings prefixed with the base32 Organization id; only their SHA-256 is stored server-side (`refresh_sessions`, tenant-owned RLS). The prefix selects the tenant scope for the lookup — a forged prefix finds no row and fails identically to a bad token. Rotation mutates the session row in place under a conditional UPDATE (`token_hash` → new, `previous_token_hash` → old); presenting an already-rotated token matches the previous hash and revokes the whole session family (replay = theft). Revocations always COMMIT before any error is raised. Consequences: replay, races and revocation are deterministic (proven by the concurrency suite); access tokens remain valid until expiry after revocation (documented trade-off, bounded by the short TTL); future phases may add proof-of-possession or reference tokens without schema changes.
