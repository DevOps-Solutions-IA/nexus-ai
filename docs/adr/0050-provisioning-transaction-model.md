# ADR-0050: Provisioning transaction model and idempotency strategy

Status: Accepted. Context: NXS-ORG-001 requires automated, transactional, idempotent, concurrency-safe, retry-safe Organization provisioning. Decision: the provisioner runs three explicit phases:

* **Phase 1 — idempotency claim** (own transaction): insert a PENDING `provisioning_requests` row keyed by SHA-256(idempotency_key) with the SHA-256 request fingerprint and the VALIDATED canonical payload snapshot (secret-free by contract; the raw key is never stored). A key-hash unique violation resolves into replay (same fingerprint + COMPLETED → the original result), deterministic conflict (different fingerprint → `NXS_PROV_IDEMPOTENCY_CONFLICT`), terminal-failure replay (`NXS_PROV_FAILED` with the recorded sanitized code), or resume.
* **Phase 2 — tenant baseline** (one transaction, with a savepoint): bind the transaction-local tenant GUC to a fresh server-generated UUIDv7, create the Organization core record (PROVISIONING), **write the exact durable attribution link request → Organization (the ledger's FK-enforced `organization_id`, committed in this same transaction — audit corrective)**, the owner membership and FIXED `org_owner` assignment (P03 primitives — no onboarding field selects a role), P05 settings, the baseline dashboard configuration and the `organizations.provisioned` outbox intent, then transition to ACTIVE. Deterministic business failures roll back to the savepoint and persist a terminal FAILED row; any infrastructure failure rolls back the whole transaction, so a partially-visible "half Organization" is structurally impossible. Outbox-insert failure rolls provisioning back (audit requirement).
* **Phase 3 — finalization** (own transaction): mark COMPLETED.

Crash semantics: a crash before Phase 2 leaves nothing (same key retries cleanly); between Phase 2 and 3 a PENDING row plus a committed Organization exists — the resume path finalizes the committed work ONLY through the request's own FK-enforced link (audit corrective: a slug lookup was removed because it could adopt another request's Organization); a PENDING claim older than `pending_stale_seconds` (60 s default, injectable) is treated as an abandoned crash and the baseline re-runs under the original claim (re-validating the stored snapshot against its own fingerprint), while a younger one answers `NXS_PROV_IN_PROGRESS` (retryable). The unique slug makes concurrent re-runs safe; exactly-once is NOT claimed — duplicate-safe effects come from the constraints. NATS is never touched synchronously; the relay publishes later, so a JetStream outage cannot corrupt provisioning.

Consequences: the operational Organization lifecycle (P02 `OrganizationStatus`) is kept separate from the provisioning workflow lifecycle (`provisioning_requests.status`); the ledger is GLOBAL (the control plane runs before tenant scope exists) and stores no secrets, payload dumps or raw idempotency keys; retries are explicit and deterministic (documented in the failure matrix).
