# ADR-0044: Authenticated tenant context resolution

Status: Accepted (amended by the independent-audit corrective). Context: ADR-0036 reserved the `TenantContextResolver` seam for P03. Decision: `BearerTokenTenantContextResolver` completes it. It reads ONLY the `Authorization: Bearer` token; no header (or a spoofed `X-NXS-Organization-ID` alone) resolves NO context, so P02's 403 `NXS_TENANT_CONTEXT_REQUIRED` contract is preserved for unauthenticated callers. A valid token's `org` claim — minted server-side strictly after membership verification — becomes the `TenantContext(organization_id, source=RESOLVED_IDENTITY)`. The token's signature binds sub/org/sid, so neither tenant nor identity claims can be altered without invalidating the token (proven by tampering tests). The header resolver remains LOCAL/TEST-only and configuration still refuses it in staging/production.

CORRECTIVE (audit Finding 1): cryptographic validity is necessary but never sufficient. Before any tenant scope is granted, the resolver runs the canonical `PrincipalStateValidator` — a single boundary re-checking LIVE server-side state inside a tenant-scoped transaction: refresh session exists and is neither revoked nor expired, user ACTIVE, membership in the token's Organization ACTIVE, Organization operational. An already-issued access token therefore stops authorizing tenant access the moment any of those states change (logout, membership revocation/suspension, user suspension, Organization suspension), with deterministic recovery when state is restored. `AuthService.session_view` / `list_memberships` use the same boundary — authorization logic is never duplicated per endpoint.

Consequences: `organization_id` never comes from headers, bodies, or global fallback; no P02 tenancy code changed; every tenant request performs one state-validation transaction (correctness over latency at this stage); failure modes are the canonical 401/403 problem-details codes, never 200.
