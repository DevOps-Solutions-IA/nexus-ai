# ADR-0042: Signing key management abstraction

Status: Accepted. Context: P03 must not hard-code a key storage design and must never expose private material. Decision: token code depends only on the `SigningKeyProvider` protocol (`signing_key`, `verification_key`, `all_kids`). The local provider derives Ed25519 keys from configured 32-byte hex seeds (inline `NXS_AUTH__SIGNING_KEY`, or a seed file); `verification_key_seeds` holds rotated keys that verify but never sign. Key identifiers are the first 16 hex chars of SHA-256(public key) — derivable from public material only. Rotation: add the old public key to the verification set and deploy; old access tokens keep verifying until they expire; remove the old key afterwards. Hardened environments fail closed at configuration time when no key material is configured, when the ephemeral development flag is set, or when key loading fails. Private material: wrapped in a repr-redacted dataclass, never returned by any API, never logged. Consequences: a future KMS/HSM/Vault provider replaces the local provider behind the same protocol without touching token code; `tests/unit/test_auth_tokens.py` proves rotated keys verify old tokens and removed keys reject them.
